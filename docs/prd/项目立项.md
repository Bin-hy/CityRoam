# 1. 产品概述

## 1.1 一句话定义

TripPilot 是一个把「我想怎么玩」变成「今天几点去哪、怎么走、花多少钱」的旅行规划 Agent。它不只生成行程，还会检查行程能不能走通，发现冲突就自动重排，并把每一次修改的原因展示给用户。

## 1.2 产品愿景

让没有时间做攻略的人，也能在几分钟内得到一份**可执行、可解释、可调整**的旅行计划。

- 可执行：营业时间、路程、预算、体力都成立。
- 可解释：每个安排都有理由，每次修改都有 diff。
- 可调整：用户改一句话，系统只重排受影响的部分。

## 1.3 产品定位

TripPilot 不是 OTA，不卖票、不订酒店、不做导航。它位于「内容攻略」和「预订平台」之间：把攻略里的灵感，变成一份真正能照着走的日程。

## 1.4 核心价值

| 对象 | 价值 |
|---|---|
| 周末短途学生 | 预算有限、时间有限，需要一份不踩坑的两日计划 |
| 毕业旅行策划者 | 多人偏好冲突，需要可讨论、可修改的方案 |
| 带父母出行的年轻人 | 节奏、体力、餐饮有硬约束，需要可解释的安排 |

## 1.5 非目标

首版不做：

- 机票、酒店、门票预订与支付。
- 实时导航、实时路况、实时排队时间。
- 多城市串联、跨城交通。
- 账号体系、多人协作、社区内容。
- 原生 App。
- 生成旅行照片、视频或数字人。
- 全国 POI 覆盖；首版只做北京。
- 替代小红书、马蜂窝等内容平台。

# 2. 问题与机会

## 2.1 用户问题

规划一次 2～3 天的旅行，通常需要在多个平台之间来回切换：

1. 在内容平台找「必去」和「避雷」。
2. 在地图里逐个搜索地点、看营业时间、算路程。
3. 在表格或备忘录里手动排时间。
4. 发现某个点周一闭馆，或者两个点之间要坐 1 小时地铁，只能推倒重排。
5. 同行人说「太赶了」，又要重新来一遍。

现有 AI 产品大多只做第 1 步：生成一份看起来不错的行程文本。它不检查营业时间，不算路程，不估预算，也不解释为什么这样排。

## 2.2 机会

大模型擅长「选点和叙事」，但不擅长「约束满足」和「精确计算」。把两者分开：

- LLM 负责理解偏好、选择候选、组织叙事。
- 确定性代码负责营业时间、路程、预算、时长校验。
- Agent 循环负责在两者之间反复修复，直到行程可执行。

这个分工让系统既有「人味」，又有「工程可靠性」。

## 2.3 与现有方案的区别

| 类型 | 代表 | 局限 |
|---|---|---|
| 内容攻略 | 小红书、马蜂窝 | 有灵感，不可直接执行 |
| 预订平台 | 携程、飞猪 | 能订票，但不负责行程是否合理 |
| 一次性 AI 行程生成 | 各类聊天机器人与小程序 | 生成文本，不校验，不解释，不追踪修改 |
| TripPilot | 本项目 | 闭集选择 + 确定性校验 + 修复循环 + 版本 diff |

## 2.4 成功假设

如果用户能在 3 分钟内得到一份 2 日行程，且这份行程的硬约束满足率达到 90% 以上，用户愿意在此基础上做不超过两次调整就接受，那么这个产品就成立。

## 2.5 项目约束

本项目同时是一个面向后端 / Agent 实习申请的作品集项目，因此：

- 总投入约 60 小时，每周不超过 10 小时。
- 单人开发，不做团队协作功能。
- 只使用 1 个 LLM，不引入图像、语音、视频模型。
- 评测数据必须可复现，指标必须可量化。

# 3. 用户画像

## 3.1 用户 A：周末短途学生

- 年龄 18～24 岁，预算 500～1000 元。
- 周五晚决定，周六早上出发。
- 关注：交通方便、人均消费、出片、不要太累。
- 典型输入：「北京两天，预算 800，想看故宫和几个博物馆，晚上想吃点好的，不要太赶。」

## 3.2 用户 B：毕业旅行策划者

- 年龄 21～26 岁，4～6 人同行。
- 需要把不同人的偏好折中成一份大家都能接受的计划。
- 关注：必去点、人均预算、每天强度、雨天备选。
- 典型输入：「四个人的毕业旅行，北京三天，有人想爬长城，有人只想拍照，预算人均 1500。」

## 3.3 用户 C：带父母出行的年轻人

- 年龄 25～30 岁，2～3 人。
- 关注：少走路、按时吃饭、室内备选、不要太晚。
- 典型输入：「带爸妈去北京两天，走路不能太多，中午要能坐下吃饭，晚上八点前回酒店。」

# 4. 核心概念

| 概念 | 定义 |
|---|---|
| Trip | 一次规划任务，包含城市、天数、预算、偏好和所有版本 |
| Constraint | 约束，分为硬约束和软偏好 |
| POI | 候选地点，来自本地快照，包含坐标、类别、营业时间、门票、建议时长 |
| Candidate Set | 本轮检索出的候选 POI 集合，LLM 只能从中选择 |
| Itinerary | 结构化行程，按天、按时间块组织 |
| Block | 行程中的最小单元：景点、餐饮、交通、休息 |
| Violation | 校验器发现的问题，包含类型、严重级别、涉及的时间块、修复建议 |
| Plan Version | 每次生成或修复产生的行程快照 |
| Agent Run | 一次完整的规划执行，包含所有工具调用和 LLM 调用记录 |
| Preference Memory | 跨行程保存的用户偏好（P1） |

# 5. 核心用户体验

## 5.1 主场景：北京两日

用户进入首页，看到一句话输入框：

> 「北京两天，预算 800，喜欢历史和咖啡，不要太赶，周一出发。」

### 阶段 1：需求解析

系统在 5 秒内返回结构化约束：

| 类型 | 内容 | 可编辑 |
|---|---|---|
| 城市 | 北京 | 是 |
| 天数 | 2 天 | 是 |
| 日期 | 下周一 | 是 |
| 预算 | 800 元/人 | 是 |
| 兴趣 | 历史、咖啡 | 是 |
| 节奏 | 轻松 | 是 |
| 硬约束 | 周一闭馆地点需排除 | 是 |
| 软偏好 | 晚上想吃点好的 | 是 |

用户可以直接修改，也可以补充「必去」和「不想去」。

### 阶段 2：规划与修复

用户点击「开始规划」，页面展示实时进度：

```
正在检索候选地点…… 找到 46 个
正在生成第一版行程……
校验发现 3 个问题：
  - 第 2 天 10:30 故宫博物院周一闭馆
  - 第 1 天 15:00 → 16:00 路程 68 分钟，超出缓冲
  - 第 2 天预算超出 120 元
正在重排第 2 天……
校验通过。
```

这里的进度不是装饰，而是 Agent 的真实执行轨迹。用户可以展开每一步，看到工具返回了什么、LLM 改了什么。

### 阶段 3：结果展示

结果页包含：

- 地图：每天一条路线，按颜色区分。
- 时间轴：每个时间块的地点、时间、交通方式、耗时、花费。
- 预算卡：门票、餐饮、交通、总计，与目标预算对比。
- 解释卡：为什么选这些点、为什么这样排序、放弃了哪些候选及原因。
- 版本切换：查看修复前的版本和违规项。

### 阶段 4：自然语言调整

用户输入：

> 「第二天太赶了，去掉一个点，下午想留点时间喝咖啡。」

系统输出调整提案：

```
将删除：798 艺术区（往返 90 分钟）
将新增：胡同咖啡馆（步行 8 分钟）
调整后：第 2 天总时长从 9.5 小时降到 7 小时
影响：门票预算减少 0 元，餐饮预算增加 40 元
```

用户可以接受、拒绝或要求重新生成。接受后生成新版本，旧版本保留。

### 阶段 5：分享与导出

用户可以获得：

- 分享链接：无需登录即可查看行程、地图和预算。
- 复制文本：适合发到微信群。
- 打印友好页面：适合出发前保存。

MVP 不提供 PDF 和日历导出，P1 再补。

# 6. 产品交互约束

## 6.1 闭集选择

LLM 只能从工具返回的候选 POI 中选择，输出中必须使用 POI ID。

- 校验器拒绝任何不在候选集中的 ID。
- POI 的营业时间、门票、坐标以快照为准，不以 LLM 输出为准。
- 如果 LLM 连续两次输出非法 ID，系统降级为规则排序并提示。

## 6.2 硬约束与软偏好

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 硬约束 | 营业时间、必去点、每日时长上限、预算上限、餐点时间、不重复 | 必须满足；无法满足时明确说明并请用户放宽 |
| 软偏好 | 节奏、兴趣比例、评分、天气偏好、出片 | 尽量满足；冲突时在解释卡中说明取舍 |

## 6.3 修复轮数上限

- 最多 3 轮自动修复。
- 3 轮后仍有硬约束冲突，输出当前最优解 + 明确的警告 + 建议放宽的约束。
- 不允许无限循环，不允许静默忽略冲突。

## 6.4 版本与差异

- 每次生成、修复、用户调整都产生新版本。
- 版本只保存行程 JSON 和约束快照，不复制地图或图片。
- 用户可以查看任意两个版本的差异。
- 删除行程时软删除，保留 7 天。

## 6.5 Agent 与确定性逻辑的边界

| 决策 | 由谁负责 |
|---|---|
| 理解用户想要什么 | LLM |
| 从候选里选哪些点、怎么讲理由 | LLM |
| 地点是否存在、是否营业、门票多少 | 确定性数据 |
| 路程时间、每日时长、预算加总 | 确定性计算 |
| 行程是否合格 | 确定性校验器 |
| 先修哪个问题 | 规则优先级 + LLM 建议 |
| 是否继续修复 | 停止条件（确定性） |

## 6.6 失败降级

| 故障 | 降级方式 |
|---|---|
| 路径 API 超时 | 使用直线距离估算 + 明确标注「估算」 |
| 天气 API 失败 | 跳过天气建议，不影响主流程 |
| POI 搜索结果为空 | 放宽类别或扩大范围，提示用户 |
| LLM 输出非法 JSON | 自动重试 1 次；仍失败则返回规则排序结果 |
| LLM 超时 | 返回上一版可用行程 + 错误提示 |
| 约束无法满足 | 输出冲突说明 + 建议放宽项，不伪造结果 |

# 7. 页面与信息架构

## 7.1 页面列表

| 页面 | 用途 | 优先级 |
|---|---|---|
| 首页 / 创建页 | 输入需求、查看示例 | P0 |
| 规划工作台 | 实时进度、行程、地图、调整 | P0 |
| 行程详情页 | 只读查看、版本切换、分享 | P0 |
| 分享页 | 无需登录查看行程 | P0 |
| 历史行程 | 查看和继续之前的规划 | P1 |
| 偏好设置 | 编辑长期偏好 | P1 |
| 评测面板 | 内部使用，查看用例与指标 | P1（开发用） |

## 7.2 首页 / 创建页

- 标题：「这周末，想去哪走走？」
- 自然语言输入框。
- 三个示例需求，点击直接填入。
- 城市选择：MVP 仅北京可用，其他城市置灰并标注「即将开放」。
- 高级选项：天数、预算、节奏、必去、不想去。

## 7.3 规划工作台

三栏布局，移动端纵向堆叠：

- 左：实时轨迹（步骤、工具调用、校验结果）。
- 中：地图 + 时间轴。
- 右：预算、解释、调整输入框、版本切换。

生成过程中，用户看到的是「正在校验第 2 天」这样的真实状态，而不是一个转圈动画。

## 7.4 行程详情 / 分享页

- 只读行程、地图、预算、解释。
- 版本列表，分享页只展示最终版本。
- 「我也来规划一版」入口。
- 明确的 AI 生成标识和数据来源说明。

# 8. 功能需求

## FR-01：自然语言需求解析

**优先级：P0**

用户用一句话描述需求，系统解析为结构化约束。

### 验收标准

- 能识别城市、天数、预算、兴趣、节奏、必去、不想去中的至少 4 类。
- 缺失关键信息（城市、天数）时主动追问，不擅自假设。
- 无法识别的信息进入「待确认」列表，由用户补充。
- 解析结果可编辑，修改后重新校验。

## FR-02：约束确认与编辑

**优先级：P0**

### 验收标准

- 硬约束和软偏好分开展示。
- 用户可以修改任意字段。
- 用户可以把软偏好升级为硬约束，反之亦然。
- 修改后，旧版本保留，新版本使用最新约束。

## FR-03：POI 候选检索

**优先级：P0**

### 验收标准

- 根据城市、兴趣、必去、日期检索候选。
- 必去点必须在候选集中；无法找到时明确提示。
- 候选集包含：ID、名称、类别、坐标、营业时间、门票、建议时长、评分、来源。
- 候选数量控制在 40～60 个，避免超出 LLM 上下文。
- 检索结果缓存 24 小时，同城同条件不重复调用。

## FR-04：行程草案生成

**优先级：P0**

### 验收标准

- 输出符合 Itinerary Schema 的 JSON。
- 每天包含起止时间、时间块、交通方式、预算。
- 只能使用候选集中的 POI ID。
- 每天至少包含一个餐饮时间块，除非用户明确不需要。
- 生成失败时保留上一版可用行程。

## FR-05：确定性校验

**优先级：P0**

校验规则至少包含：

1. 营业时间：到访时间必须落在营业时间内。
2. 闭馆日：周一闭馆等规则。
3. 路程时间：相邻时间块之间的路程 + 缓冲。
4. 每日时长：不超过用户设定或默认上限。
5. 预算：门票 + 餐饮 + 交通不超过上限。
6. 餐点：午餐、晚餐时间窗。
7. 必去点：全部包含。
8. 重复：同一 POI 不跨天重复。
9. 节奏：每日 POI 数量符合轻松 / 正常 / 紧凑。
10. 起止时间：不早于用户设定，不晚于用户设定。

### 验收标准

- 校验器为纯函数，可单独测试。
- 每个违规项包含：类型、严重级别（阻断 / 警告）、涉及的时间块、修复建议。
- 警告不阻断输出，阻断项必须修复或明确告知。

## FR-06：自动修复循环

**优先级：P0**

### 验收标准

- 每轮把违规项和替代候选回灌给 LLM。
- 优先局部修复：只重排受影响的那一天或那个时间块。
- 最多 3 轮；每轮记录修复前后的差异。
- 修复后重新校验，不允许跳过校验直接输出。
- 3 轮后仍有阻断项，输出最优解 + 警告 + 建议放宽的约束。

## FR-07：自然语言调整与重规划

**优先级：P0**

### 验收标准

- 能识别调整对象：某一天、某个时间块、某个 POI、整体节奏、预算。
- 输出调整提案：改什么、为什么、影响是什么。
- 用户接受后才生成新版本；拒绝则保留原版本。
- 只重排受影响范围，不无故改动其他天。
- 无法理解时追问，不猜测。

## FR-08：版本管理与差异

**优先级：P0**

### 验收标准

- 每次生成、修复、调整都产生版本。
- 版本包含行程 JSON、约束快照、违规记录、生成原因。
- 支持查看任意两个版本的差异。
- 支持回退到上一版本继续调整。
- 版本数量不设硬上限，但超过 20 个时提示用户清理。

## FR-09：地图与时间轴展示

**优先级：P0**

### 验收标准

- 地图按天展示路线，颜色区分。
- 时间轴与地图联动：点击时间块高亮对应地点。
- 显示交通方式、耗时、花费。
- 移动端可读，不依赖悬停。
- 地图加载失败时，时间轴和文本信息仍然可用。

## FR-10：分享与导出

**优先级：P0**

### 验收标准

- 生成无需登录的分享链接。
- 分享页包含行程、地图、预算、AI 标识、数据来源。
- 支持复制纯文本行程，适合发群。
- 分享页只展示最终版本。
- 未主动分享的行程不公开。

## FR-11：偏好记忆

**优先级：P1**

### 验收标准

- 记录用户常用节奏、兴趣、预算区间、不想去的地点类型。
- 下次规划时默认带入，可修改。
- 用户可以查看和删除记忆。
- 记忆不影响硬约束。

## FR-12：评测与可观测

**优先级：P0（内部能力）**

### 验收标准

- 每次 Agent Run 记录完整 trace：步骤、工具调用、LLM 调用、耗时、token、错误。
- 内置 20 条评测用例，覆盖 1～4 天、不同预算、不同节奏、必去、雨天。
- 可一键跑评测并输出指标表。
- 失败用例可回放到具体步骤。

## FR-13：多城市扩展

**优先级：P2**

### 验收标准

- 新增城市只需增加 POI 快照和配置，不改核心代码。
- 城市不支持时，首页明确提示。

## FR-14：实时变更提醒

**优先级：P2**

### 验收标准

- 出发前检查天气和营业状态。
- 发现变化时提示用户并给出替代方案。
- 不自动修改已确认的行程。

# 9. Agent 行为设计

## 9.1 逻辑职责

| 角色 | 职责 | 实现方式 |
|---|---|---|
| Planner | 理解需求、选择 POI、组织行程 | LLM |
| Validator | 检查营业、路程、预算、时长、餐点 | 确定性代码 |
| Repairer | 根据违规项局部重排 | LLM + 规则 |
| Presenter | 生成解释、差异、警告 | LLM + 模板 |
| Reviewer | 检查输出结构、ID 合法性、叙事一致性 | 规则 + 轻量 LLM 检查 |

这些是逻辑职责，MVP 不拆成多个服务。

## 9.2 工作流

1. **Admit**：校验城市是否支持、输入是否为空、是否包含不安全内容。
2. **Parse**：自然语言转约束 JSON；缺失关键信息则追问。
3. **Retrieve**：检索候选 POI，确保必去点在集合内。
4. **Draft**：LLM 从候选集中选择并排序，输出 Itinerary。
5. **Validate**：确定性校验，输出违规列表。
6. **Repair**：有阻断项则局部重排，回到 Validate；最多 3 轮。
7. **Present**：输出地图、时间轴、预算、解释。
8. **Interrupt**：等待用户调整或确认。
9. **Replan**：解析调整意图，确定影响范围，局部重排。
10. **Finalize**：生成版本快照、分享链接。

## 9.3 工具

| 工具 | 输入 | 输出 | 失败处理 |
|---|---|---|---|
| search_poi | 城市、关键词、类别、区域 | POI 列表 | 扩大范围重试一次 |
| get_poi_detail | POI ID | 营业时间、门票、建议时长 | 返回快照数据并标注「待确认」 |
| route | 起点、终点、交通方式 | 距离、耗时 | 直线距离估算并标注 |
| weather | 城市、日期范围 | 天气预报 | 跳过，输出无天气建议 |
| validate_itinerary | Itinerary | 违规列表 | 校验器异常视为阻断，不输出 |
| geocode | 地址 | 坐标 | 失败则要求用户从候选选择 |

## 9.4 状态机

```
draft → parsing → retrieving → planning → validating
      → repairing → validating → ... → awaiting_user
      → replanning → validating → ... → completed
```

- `awaiting_user` 可以长时间停留。
- `cancelled` 和 `failed` 是终态；迟到的异步回调不得把终态改回进行中。
- `completed` 后再次调整会创建新版本，不改变旧版本。

## 9.5 停止条件

满足任一条件即停止修复：

1. 所有阻断项清零。
2. 达到 3 轮上限。
3. 连续两轮违规数量没有下降。
4. 用户主动取消。

停止后必须输出：当前最优行程、剩余违规、原因、建议。

## 9.6 记忆

- 单次行程：约束、版本、用户调整、违规历史。
- 跨行程（P1）：节奏偏好、兴趣、预算区间、不想去的类型。
- 记忆只影响软偏好，不覆盖硬约束。
- 用户可查看、修改、删除。

## 9.7 结构化输出

- 所有 LLM 输出使用 JSON Schema 约束。
- 解析失败自动重试 1 次，附带错误信息。
- 行程中的 POI ID 必须是候选集 ID。
- 解释文本与结构化字段分开，避免叙事污染数据。

## 9.8 可观测性

- 每次运行生成 `run_id`。
- 记录每一步的输入、输出、耗时、token、错误。
- 前端可展开查看 trace。
- 评测面板按用例聚合指标。

# 10. 数据设计

## 10.1 核心实体

| 实体 | 说明 |
|---|---|
| Trip | 一次规划任务 |
| PlanVersion | 行程版本 |
| ToolCall | 工具调用记录 |
| PoiCache | POI 快照 |
| EvalRun | 评测运行记录 |
| Preference | 用户偏好（P1） |

## 10.2 表结构

```sql
CREATE TABLE trips (
  id uuid PRIMARY KEY,
  city text NOT NULL,
  days int NOT NULL CHECK (days BETWEEN 1 AND 4),
  budget int,
  preferences jsonb NOT NULL,
  status text NOT NULL,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

CREATE TABLE plan_versions (
  id uuid PRIMARY KEY,
  trip_id uuid NOT NULL REFERENCES trips,
  seq int NOT NULL,
  plan jsonb NOT NULL,
  violations jsonb NOT NULL DEFAULT '[]',
  reason text,
  created_at timestamptz DEFAULT now(),
  UNIQUE (trip_id, seq)
);

CREATE TABLE tool_calls (
  id bigserial PRIMARY KEY,
  trip_id uuid NOT NULL REFERENCES trips,
  run_id uuid NOT NULL,
  tool text NOT NULL,
  input jsonb NOT NULL,
  output jsonb,
  latency_ms int,
  error text,
  created_at timestamptz DEFAULT now()
);

CREATE TABLE poi_cache (
  id text PRIMARY KEY,
  city text NOT NULL,
  name text NOT NULL,
  category text NOT NULL,
  lat double precision NOT NULL,
  lng double precision NOT NULL,
  open_hours jsonb,
  ticket_price int,
  suggested_minutes int,
  rating numeric(2,1),
  source text,
  fetched_at timestamptz DEFAULT now()
);

CREATE TABLE eval_runs (
  id uuid PRIMARY KEY,
  case_id text NOT NULL,
  metrics jsonb NOT NULL,
  created_at timestamptz DEFAULT now()
);
```

## 10.3 数据来源

- POI 基础信息：人工整理的北京快照（40～60 个），标注来源和核对日期。
- 路径与天气：高德 Web 服务 API。
- 地图底图：高德 JS API（已确认），统一 GCJ-02。

## 10.4 数据保留

- 行程和版本：保留至用户删除后 7 天。
- 工具调用：保留 30 天，用于排查。
- 评测记录：长期保留。
- 不采集用户身份信息。

# 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| POI 营业时间不准 | 行程不可执行 | 人工核对快照，标注核对日期；未知时标注「待确认」 |
| 地图 API 配额或坐标问题 | 路程计算错误 | 缓存 + 直线距离降级；统一 GCJ-02 |
| LLM 编造地点 | 结果不可信 | 闭集选择 + ID 校验 + 非法即重试 |
| LLM 输出结构不稳定 | 流程中断 | JSON Schema + 一次重试 + 规则兜底 |
| 修复循环不收敛 | 延迟和成本上升 | 3 轮上限 + 连续无改善即停 |
| 范围蔓延 | 六周做不完 | 严格的非目标清单；每周验收 |
| 「又是一个行程生成器」 | 面试缺乏记忆点 | 强调校验-修复循环、trace、评测数据 |
| demo 现场翻车 | 作品集减分 | 确定性核心 + 本地缓存 + 录屏兜底 |
