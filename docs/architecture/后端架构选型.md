## 1. 结论

- **模块化单体**，不拆微服务。
- **Go 1.24+ + Eino**：Eino Graph 负责编排，领域代码保持确定性。
- **PostgreSQL 16** 为唯一持久化存储，不引入 Redis / 消息队列。
- LLM 只负责解析、选点、解释；校验和计算用确定性代码。
- 插件边界用 **MCP**，不自研协议；核心工具 native，第三方按需 MCP。
- **SSE** 推送进度，**Docker Compose + Caddy** 单机部署。

## 2. 选型记录

### 2.1 候选对比

| 候选 | 结论 | 原因 |
|---|---|---|
| Python + FastAPI + 手写 Kernel | 备选 | 交付最快、LLM/MCP 生态最顺；类型安全弱，性能余量小 |
| Python + PydanticAI / LangGraph | 备选 | 类型化和图编排更好；仍依赖 Python 运行时 |
| Go + 手写状态机 | 可行 | 性能、单二进制、类型安全；图、流式、回调要自己写 |
| **Go + Eino** | **选定** | 类型安全、Graph 编排、回调/流式、字节生态；性能余量大 |
| LangChain / Dify | 不采用 | 抽象或平台锁定，且不解决领域校验 |

### 2.2 为什么是 Go + Eino

1. **性能余量**：Go 内存约 30～80MB，并发和冷启动更好；2C4G 上留足余量。
2. **类型安全**：Agent 生成代码时编译器兜底；Eino 的强类型 State/Graph 减少运行时错误。
3. **编排能力**：Eino Graph 有条件边、状态、回调、流式；修复循环可直接表达。
4. **字节生态**：Eino 是 CloudWeGo 项目，与剪映/字节技术栈契合。
5. **单二进制**：API、Agent、核心工具同进程，镜像小、部署简单。

### 2.3 代价与边界

- 端到端延迟仍由 LLM 决定；Go 不会把 15 秒变成 5 秒。优化靠并行、缓存、减少 LLM 调用。
- 结构化输出不如 Pydantic 顺手：JSON Schema + 校验器 + 一次重试。
- MCP 生态不如 Python：用 Go MCP SDK/适配器包成 Eino Tool。
- Eino 只负责编排：C1–C12、预算、时间轴、POI 数据仍然自己写。

## 3. 架构

```
Browser
  │ HTTPS + SSE
Caddy
  │ /api/*
Go API（chi，单二进制）
  ├─ api/            路由、入参校验、SSE
  ├─ agent/          Eino Graph：parse → retrieve → draft → validate → repair
  ├─ domain/         校验器、预算、时间轴（纯函数）
  ├─ mcp/            McpHub：连接、发现、超时、预算、trace
  ├─ tools/          高德 / 快照 / 直线距离 / 天气（native）
  ├─ repo/           pgx + sqlc
  └─ events/         SSE 事件
        │
     PostgreSQL 16
        │
   高德 API / LLM API
```

边界原则：`domain/` 不依赖 HTTP、Eino 和数据库；`agent/` 只依赖接口；`api/` 不写业务逻辑。

## 4. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | Go 1.24+ | 类型安全、单二进制、并发 |
| Agent 编排 | **Eino** | Graph/State/回调/流式 |
| Web | chi + net/http | 轻量、idiomatic，SSE 用 `http.Flusher` |
| 数据库 | PostgreSQL 16 | 关系 + JSONB |
| 数据访问 | pgx/v5 + sqlc | 类型安全 SQL，编译期检查 |
| 迁移 | goose | 简单、可嵌入 |
| 校验 | go-playground/validator + jsonschema | 入参 + LLM 输出 |
| LLM | Eino ChatModel（OpenAI 兼容） | DeepSeek / Qwen 可替换 |
| MCP | Go MCP SDK | 标准协议；核心工具 native |
| 流式 | SSE + `http.Flusher` | 单向进度 |
| 日志 | log/slog | 标准库 |
| 追踪 | OpenTelemetry Go | 标准 trace |
| 测试 | testing + testify | 单测 + 集成 |
| 部署 | Docker + Caddy | 单机 2C4G |
| CI | GitHub Actions | vet / lint / test / build |

## 5. Eino 映射

- 节点：parse / retrieve / draft / validate / repair / present。
- 状态：`TripState`，包含约束、候选、行程、违规、轮次。
- 条件边：validate 后根据阻断项走 repair 或 present；repair 回到 validate。
- 工具：确定性调用用 Lambda 节点；需要 LLM 选工具时用 `ToolsNode`。
- MCP：包成 Eino Tool 或 Lambda 节点，McpHub 设计不变。
- 流式：Eino callback → SSE。
- 闭环原则：LLM 提议，校验器裁决，修复循环兜底；Eino 只负责连边和状态。

## 7. 性能

端到端瓶颈是 LLM，不是语言。Go 的收益在内存、并发、冷启动和类型安全。

| 手段 | 做法 |
|---|---|
| 并行检索 | `errgroup` 并发调 POI / 路径 / 天气，限制并发 |
| 缓存 | POI 常驻内存 + Postgres；路径 / 天气 24h |
| 少调 LLM | 只 repair 受影响的天；最多 3 轮 |
| SSE | 边算边推，降低感知延迟 |
| 数据库 | pgx 连接池 + sqlc 预编译 |
| 外部 HTTP | keep-alive、超时、退避重试 |
| 核心工具 | native，避免 MCP IPC；第三方才走 MCP |
| 观测 | OTel + pprof，先测再优化 |

## 8. 部署

```
Caddy（TLS + 静态资源）
  ├─ /        → 前端
  └─ /api/*   → api:8080
                 ├─ postgres:5432
                 └─ 可选 mcp-search / mcp-xhs
```

- 多阶段构建，最终镜像只含二进制和配置。
- 单实例运行；密钥走环境变量；每日 `pg_dump`。
- `/healthz` 健康检查；GitHub Actions 构建和测试。

## 9. 明确不做

- 不拆微服务，不引入 Redis / Celery / Kafka / K8s。
- 不把 LangChain / Dify 放进核心链路。
- 不自研插件协议、鉴权、trace 格式。
- 不做酒店、机票、支付、实时公交、多城市。
- 不做对象存储。
